## Facts verified by the orchestrator (do not re-audit; read only the files you need)

- `FnbInventoryService.recordMovement`: checks `inventory.movementByKey(tenantId, key)`; if present with the SAME fingerprint it replays the stored movement (HTTP 201), with a different fingerprint -> `OperationConflictException` (409). If absent: loads the balance, `inventory.lock(balance)` (= `entityManager.refresh(PESSIMISTIC_WRITE)`), `apply(delta)`, persists the movement, flushes. The check-then-insert is NOT atomic: two parallel requests with the same key can both pass the check; the loser then violates the unique `(tenant_id, idempotency_key)` index, its transaction rolls back (including its balance change) and `GlobalExceptionHandler` maps `DataIntegrityViolationException` to 409. So the LEGAL outcome set for N parallel identical requests is: >= 1 response 201 and every other response 201 (replay, same movement id) or 409; never 5xx; the balance is applied EXACTLY once.
- `FnbPaymentService.pay` takes `orders.lockTenant(tenantId)` first (serialises all payments of one tenant), then calls `settle(...)`, which calls `FnbStockService.consumeForPaidOrder`: one SALE movement per (order, ingredient) with key `sale:{orderId}:{inventoryItemId}`, balance locked per ingredient, ordered by ingredient id. Stock may go negative; a payment is never blocked by stock. Payment idempotency: same key + same fingerprint replays, different fingerprint -> 409; a second payment of an already-paid order with a different key is rejected (existing test `concurrentPaymentsWithDifferentKeysSettleExactlyOnce` proves exactly-one-payment, but NOT the stock side).
- Manual movements lock only the balance row; payments lock the tenant row then balance rows. No lock-order cycle is expected; the mixed test below proves it empirically (a deadlock would surface as a 5xx / timeout).
- Invariant of the ledger: `inventory_balances.quantity_on_hand == SUM(inventory_movements.quantity_delta)` per (tenant, outlet, item).

A. Same movement key, same payload, in parallel: ingredient with stock 0; 8 parallel `RESTOCK` of 100 with ONE shared `idempotencyKey`. Assert: no 5xx; at least one 201; every non-201 is 409; all 201 bodies carry the same movement id; DB has exactly ONE movement for that key; balance == 100 exactly; ledger invariant holds.
B. Same movement key, DIFFERENT payload, in parallel: 8 parallel requests sharing one key but with different quantities (100, 101, ... ) . Assert: no 5xx; exactly one distinct movement id is ever returned in 201 bodies; every other response is 409; exactly one movement row for the key; balance == that movement's delta; invariant holds.
C. Distinct keys in parallel: 10 parallel `RESTOCK` of 10 each (unique keys) plus 5 `WASTE` of 4 each on one ingredient starting from 100. Assert: all 15 are 201 (no lost update); balance == 100 + 100 - 20 == 180; exactly 15 movements with those keys (+ the initial one); invariant holds.
D. Parallel payments of DIFFERENT orders sharing one ingredient: ingredient stock 1000 g, product recipe 50 g/unit; create 8 unpaid orders (1 unit each) via the POS checkout; pay all 8 in parallel (unique payment keys). Assert: all 8 payments succeed (200/201 as the existing tests assert), 8 SALE movements of -50 (one per order, key `sale:{orderId}:{itemId}`), balance == 600 exactly, invariant holds, each order is PAID exactly once, no 5xx.
E. Parallel payments of the SAME order: (E1) 8 parallel pays with the SAME payment key -> exactly one payment row, all successful responses refer to the same payment, exactly ONE SALE movement for the order, stock deducted once. (E2) a second order, 8 parallel pays with DIFFERENT keys -> exactly one success, the rest rejected with a 4xx (assert the status the existing test asserts), exactly ONE SALE movement, stock deducted once.
F. Mixed load, no deadlock: on one ingredient run in parallel 4 payments (different orders, recipe-bearing), 4 manual `RESTOCK` and 4 manual `WASTE` (unique keys) released together. Assert: every request finishes within the timeout (no deadlock), no 5xx, final balance == initial + restocks - wastes - sale deductions, invariant holds.
G. Negative stock stays non-blocking under load: ingredient stock 100, recipe 50 g, 6 parallel payments for 6 different orders -> all 6 succeed, balance == -200, 6 SALE movements, the last payment responses carry `stockWarnings` containing the "minus" warning text used by the existing inventory test (copy the exact wording from it).
