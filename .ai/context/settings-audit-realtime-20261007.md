# Reviewed architecture brief: settings, audit viewer, F&B real-time

Approved implementation scope from user, 2026-10-07. Baseline memory 4; reservations recorded at memory 5. Orchestrator owns this brief and tasks; workers own application writes. Existing dirty source is baseline, not expendable. No tests/build/startup/database changes in workers.

PRD coverage: 8.2 business settings, 8.7 order updates, 8.11 audit viewer; AC-01 tenant isolation, AC-04 shared order visibility. Active three-role Pay First flow remains authoritative. Backend only.

## TASK-030: owner settings

GET/PUT `/api/v1/merchant/outlets/{outletId}/business-settings`, owner only through HTTP and MerchantAccessGuard.requireOwner. Tenant from principal. Full PUT of businessName, logoUrl (optional HTTPS absolute URL, no fetching/upload), currency (uppercase ISO-4217 with two fraction digits compatible with current money implementation), address, phoneNumber, taxRate, serviceChargeRate, outletName, outletAddress, outletPhoneNumber, timeZone. Required names/timeZone/currency/rates; validate sizes matching existing columns; rates 0..100 with at most two decimals. Optional strings null/blank clear them. Outlet time zone is authoritative; mirror requested timeZone into tenant default for initial consistency, no mutation of other outlets.

Use existing tenant/outlet columns; no migration. Named entity methods, DTOs, mapper; no generic setters. Lock tenant via existing FnbOrderRepository.lockTenant, then load guarded context. Tax/service changes apply to future checkouts; existing order snapshots untouched. Currency change is rejected if tenant has any SalesOrderEntity or CashierSaleEntity, including unpaid/cancelled records (no per-order currency snapshot currently). Query via Blaze-Persistence. No-op PUT does not create audit. Changed PUT records BUSINESS_SETTINGS_CHANGED with actor/tenant/outlet/time, structured before/after settings details; no credentials. Constructor cycles prohibited. TASK-030 alone owns addition to AuditLogEntity.Action. Response includes current values, nulls omitted.

## TASK-031: audit viewer

GET `/api/v1/merchant/outlets/{outletId}/audit-logs`, requireOwner. Read only. Filter optional startDate/endDate in outlet zone (default today; max 366 inclusive days), action (bounded string, allow historical actions), actorId and entityType; page default0,size20/max100,page max1000000. Stable newest-first createdAt,id. Query/count both tenant AND outlet, always exclude null-outlet tenant/global audit rows. Include id,createdAt,local timestamp,action,entityType,entityId,actorId,actor display name if available,reason,details, pagination total/hasNext. No entities or actor email/password/session fields. Actor name means current display name, not immutable snapshot. No detail endpoint needed. New MerchantAuditRepository avoids contention with write-only AuditLogRepository and TASK-030 enum writes. CSV not included.

## TASK-032: WebSocket

Native Spring WebSocket, JSON invalidation notifications, no STOMP/SockJS or public customer subscription. POST `/api/v1/cashier/outlets/{outletId}/fnb/realtime-ticket` with Bearer JWT, Owner/Cashier via HTTP and guard, returns single-use cryptographic random ticket, expiresAt, websocketPath `/api/v1/fnb/realtime`, protocol `cashier-fnb-v1`. Re-decode existing request Bearer using configured JwtDecoder to capture access expiry; compare claims/current converter principal to request principal. Store only ticket digest, principal/outlet/expiry in bounded in-memory map; lifetime <=30s and JWT expiry. No tokens in logs/URL. Client `new WebSocket(url, ['cashier-fnb-v1', 'ticket.' + ticket])`; handshake consumes exactly one ticket from subprotocol header, rechecks guard; negotiates only `cashier-fnb-v1`. Unknown/missing/expired/used ticket rejected. Allow only exact GET handshake route anonymously in HTTP security; interceptor performs ticket authorization before upgrade. Configurable explicit allowed origins (default existing localhost frontend origins), never wildcard.

Automatically bind session to principal tenant/outlet, no client-selected tenant/subscription. No client mutation/messages accepted. Close at JWT expiry and access revocation; check current guard and expiry before every delivery and periodic cleanup. Bound ticket/session maps and per-principal slots, serialize session writes / limit send time+buffer, clean disconnections, no blocking sockets inside business transactions. Polling endpoints remain unchanged. Live delivery is best effort in one JVM, no replay or cluster guarantee; reconnect must REST resync.

Publish immutable application event snapshots within transactions for new QR/POS order, manual/mock payment settlement, pending/failed mock attempt, discount, cancellation, kitchen prepare/ready/complete. After-commit listener (fallbackExecution=false) sends only minimal payload: eventId,type,orderId,outletId,orderStatus,paymentStatus,occurredAt,resyncRequired=true. Do not include monetary or customer/item data; client fetches authorized REST data. No replay on checkout/payment idempotent return. Listener exceptions must not turn committed writes into apparent failure. Listener guard reads use separate read-only REQUIRES_NEW transaction after commit. Any framework-required `WebSocketMessage<?>` or `Map<String,Object>` override must be isolated to adapter and documented (wildcard exception only if exact external interface demands it). No application-boundary wildcard DTOs.

## Delegation and review

Three independent workers with disjoint allowlists. Settings owns tenant/outlet entity changes and audit action; audit owns new read paths; real-time owns operational service hooks, pom and SecurityConfiguration. Save per-task baseline SHA-256 for all source/pom before launch. Workers acknowledge memory5/reservation and persist report after meaningful checkpoints. No canonical writes, SQL, tests, nested agents, git reset/checkout/clean/commit. Orchestrator reviews reports AND actual baseline diff, retains user changes, requires revisions through same reserved worker when needed and persists reviewed results.

References: Spring WebSocket handshake API https://docs.spring.io/spring-framework/reference/web/websocket/server.html and transaction-bound listeners https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html . Framework docs consulted during design; native handshake ticket is this project's design choice.
